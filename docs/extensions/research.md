# Research

`sideroom_research` lets the parent agent delegate a concrete question. The
parent is instructed to use it proactively for non-trivial work that requires
exploring code, without waiting for the user to request it. It skips greetings,
general questions and obvious changes, and respects a user request not to use
research. If research is unavailable or fails, the parent continues its own
investigation and reports the limitation. The parent still asks the user,
makes decisions, changes files and runs checks. This is an instruction to the
model, not a gate: the tool does not force a call. Research runs in the background. Its report is sent to the active run, or starts a new run when the parent is idle.

The parent supplies `question`, `intendedChange`, `knownContext`, `scope` and
`depth` (`focused`, `standard` or `deep`). One call is one investigation. Pi
uses the current model and its configured provider. Identical requests in the
same project cannot run at the same time. The call returns a start acknowledgement; the report arrives as a separate session message. Session changes, branch navigation, shutdown and cancellation of the parent cancel active research and discard late results. Cancellation is cooperative. No Sideroom file is created in the project.

## Access and privacy

The researcher runs only in a trusted project on Linux or WSL with
`/proc/self/fd`. It can list directories, read project files, search literal
text in specified files, and inspect a current file's diff against HEAD or up
to ten commit subjects. Git commands are fixed; there is no general shell,
file mutation tool, test runner, nested agent or user questionnaire. Direct
`.git` access and symbolic links are blocked.

The model decides which project files are relevant. **Hidden files, ignored
files and files with sensitive names are not automatically excluded.** Their
contents can be sent to the configured model provider. Do not run research in
a project containing credentials or sensitive material that the provider must
not receive. The instructions ask the model to avoid unrelated secrets, but
that is not an access control. Hard links, mounted filesystems and concurrent
directory moves are not isolated by an operating-system sandbox.

There is no web integration in this version. The report says so and marks web
references unverified. No project content is sent to an external search
service. Use the parent agent's normal workflow for any external research that
can be performed without disclosing private content.

## Limits and results

The default time limit is 30 minutes, including finalization. Some of that time
is reserved to check evidence and return a report. The model's advertised
context window applies at every depth; Sideroom sets no separate byte cap. Near
that window, the researcher is asked to stop and produce a partial report. It
uses the provider's latest token usage and Pi's estimate for later messages,
with up to Pi's 16,384-token reserve (at most one quarter of the window). The
estimate can be wrong or a single tool result can exceed the remaining space;
in either case the provider may reject the final request and only earlier
partial evidence can be recovered. Generated output is capped at 256,000 bytes
across the investigation and any correction attempt.
The delivered report is capped at 256,000 bytes. If it is too large, it omits
material in stages and reports what was omitted. An especially large result can
lose the report or request text, but still returns a valid partial result. There
is no independent token or tool-call spending cap.

The operator may lower the limits with these environment variables. The model's
request cannot raise them. `SIDEROOM_RESEARCH_CONTEXT_BYTES` no longer changes
the context window; remove it from existing configurations.

| Variable | Default | Allowed range |
| --- | ---: | ---: |
| `SIDEROOM_RESEARCH_TIMEOUT_MS` | 1800000 | 1000 to 1800000 |
| `SIDEROOM_RESEARCH_OUTPUT_BYTES` | 256000 generated bytes | 1024 to 256000 |

A file must be at most 64,000 bytes. Reads show up to 200 lines per file at a
chosen line offset and truncate long lines. Search checks the complete content
of up to 200 lines per file, accepts up to 20 explicit files and returns at most
50 bounded excerpts around matches. A directory scan visits at most 1,024 entries and
shows at most 200 of those. Each Git command is limited to 32,000 bytes and two
seconds; a diff or history request first checks the worktree. Git inspection
requires the current file to be readable,
so deleted files cannot currently be inspected this way. An incomplete search
or listing says so; no result does not prove absence.

The report separates observed findings, inferences and pending questions. It
includes references, proposed verification and the reason it stopped. The
result also includes the request, Git revision when available, file SHA-256
hashes, evidence checks and available time, call and token counts. A hash is
made from the complete bytes read, including lines not shown. The tool checks
those hashes before returning; the parent must compare them again before later
reuse. A commit alone does not identify local changes. Research token counts appear in the report separately. Pi's public tool usage API attaches usage to the initial tool result, but the research has not finished at that point; it does not provide an API to add later usage to the session total. That total therefore excludes background research.

If the report cites project files the researcher did not read, it gets one
opportunity to read them and correct the report within the same time and output
limits. It does not retry when the context is nearly full. If the correction
fails, the first report is retained as partial. References added by the
correction are checked too, but do not trigger another attempt.

Unread, changed or unavailable references become pending and remove the
recommendation. The original conclusion is retained separately as unverified.
The checks establish which files were read and whether their bytes changed;
they do not prove the model's interpretation or quoted text is correct. The
parent must review the evidence. A run stopped by cancellation or a limit
returns a partial report when possible; if the model did not save one, bounded
excerpts from successful tool calls are used instead. Missing material is
reported, not treated as a completed answer. A parent cancellation discards the report instead of delivering a partial result. Cancellation is cooperative: an unresponsive provider or filesystem operation may not stop immediately. The extension retains a report until Pi records its message. If it remains unconfirmed, the extension retries every five seconds while the agent is idle and the same branch remains active. A synchronous failure is also retried on the next agent start. Pi's send API does not report asynchronous failures to the extension; a slow first delivery can therefore be duplicated by a retry. Pending reports do not survive shutdown.

## Evaluation

The automated suite uses simulated providers and temporary projects. It checks
request and report validation, tool restrictions, limits, cancellation,
concurrent duplicates, Git commands, file fingerprints and changed evidence.
It also runs the Pi agent and registered tool with a simulated provider; those
tests do not establish model judgment quality.

A separate real-model evaluation called the registered tool directly with Pi's
configured `openai-codex/gpt-6.1-terra` provider and five temporary projects. It
did not run inside a full interactive Pi session and did not use web access.
The fixture files contained no private project code.

| Scenario | Finding and reference review |
| --- | --- |
| Focused question | Reported `price * quantity` and cited `price.ts` and `total`. |
| Two modules | Traced `answer` to `double`, cited both modules and derived `answer(3) = 7`. |
| Documentation for another version | Cited the 2.0.0 dependency and the 1.0 document separately; blocked on missing 2.0.0 evidence rather than asserting the API existed. |
| Contradictory evidence | Cited code value 2 and documentation value 5; marked the decision as blocking and the report partial. |
| Time exhausted | Returned `timed_out` and a partial report with a blocking unanswered question; no evidence was invented. |

The two-module answer put the calculated result in its conclusion without a
separate finding labelled as an inference. An earlier contradiction run found
both values but marked the decision as non-blocking. The instructions were
corrected and the scenario was rerun; one successful rerun does not guarantee
future model answers. A prior version scenario also returned a complete status
with a blocking question. The parser now marks that combination partial and
reports the correction. The version fixture contained only a dependency
declaration, not an installed package. These checks do not replace reviewing
real project findings or checking references before use.
